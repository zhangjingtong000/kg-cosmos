# 档案留存纪律（ARCHIVE POLICY）

> **用户 2026-09-15 明确的一条纪律**（原话）：
> 「**被替代的地方不要直接删除，而是要留存档案，这一点要明确。**」
>
> **本文把这条纪律写清楚**：它为什么重要、具体怎么做、
> 什么情况下允许真删、以及本项目现在的遵守情况。

---

## 一、为什么这条纪律重要

**因为"为什么改"比"改成了什么"更容易丢。**

代码的最终形态 `git log` 能追回来；但**当时为什么这么改、被替掉的是什么、
替掉它的理由站不站得住** —— 这些**只存在于被删掉的那份东西里**。
删掉之后，下一个读代码的人（包括三个月后的自己）只会看到"现在是这样"，
**而看不到"曾经那样、以及为什么不行"**。

**这个项目尤其需要它**，因为它最有价值的产出恰好是**负结果**：
- 「人工金标这条路构不成分母」（α = −0.0119）；
- 「914 倍」与「597 倍」的差异根因；
- 「JSON Schema 约束解码从未接入生产路径」；
- venue 语义污染的四套计数。

**这些全都是"曾经那样、后来发现不行"的记录。** 删掉其中任何一条，
项目就少一个"我们真的验证过"的证据。

---

## 二、三种留存方式（按优先级）

| 方式 | 做法 | 什么时候用 |
|---|---|---|
| **A · 原地标注**（**首选**） | **文件/代码不动**，在它旁边加「⚠️ 已被 XX 替代（日期）—— 原因」 | **绝大多数情况**。改动最小，读者一眼能看到"这个还在、但别用了" |
| **B · 移入归档目录** | 移到 `docs/archive/` 或 `data/quality/archive/`，原位置留一行指针 | 当原位置**确实会误导人**（如一个会跑的旧脚本）时 |
| **C · 真删 + 记录**（**最后手段**） | 删除，但在 `CHANGELOG.md` / `REPO_HYGIENE.md` 里写清**何时删的、删了什么、为什么** | **只有在文件本身有害时**（如含密钥、或一个会误覆盖数据的脚本） |

**默认永远是 A。** 选 B 或 C 时，**必须在提交信息里写明为什么不能用 A**。

## 四、对"即将发生的事"的具体约束

### 4.1 K1（改图）—— 最重要的一处

改图会动到图数据。**必须**：
- 改前记 **before 档案**（`data/quality/metrics-archive-<ts>.json`，含 L1–L9 全层）；
- 改动**以"计划文件"形式提交**（先例：`venue-rewrite-plan.json`），**批处理脚本执行**；
- 改后记 **after 档案**，与 before 并列；
- **原始图快照保留**（先例：`data/quality/backup/graphs-*`）。

**⚠️ 已知缺口**：`metric_provenance.py:181` 目前是**覆盖写单版本，从不归档旧的一套**
（先例 `sync_graph.py:197-200` 的备份**只留 `{nodes, edges}` 两个数**）。
**这正是 TODO 的 N1**：K1 之前必须先补"指标档案机制"。

### 4.2 BUG-1（消歧判据的 3 个失败测试）

修判据会改变全库实体数。**必须**：
- 保留**旧判据的行为记录**（用 `tools/l2_disambig_eval.py` 在改前跑一遍，存档）；
- 改后重跑，**两个结果并列**；
- **不删** `tests/test_name_dedup_similarity.py` 里那 3 个断言 ——
  它们是"期望行为"的档案。

### 4.3 文档层面

- **不删**已作废的规划文档（如 `ROADMAP.md` 已过期，但**保留并标注**）✓ 已经这样做了；
- **不删**评审报告（`REVIEW_ROUNDUP.md` / `REVIEW_ACCEPTANCE.md` 都保留了被推翻的说法）；
- **重命名要谨慎**：改名会让 `docs/` 里的大量引用失效 ——
  这也是"留存"的一种（**路径也是接口**）。

## 五、论文归档（**数据层的留档**）

前四节讲的是**文件与文档**的留存。这一节讲**论文条目**的归档 ——
它是 2026-09-19 出现的一种状态（`_manifest.json` 与 `paper-registry.json`
里的 `archived` 字段组），**本文此前通篇没有提**。

⚠️ **这就是补写这一节的原因**：`web/kg-data/paper-registry.json` 的 `known_gaps`
与 `web/papers.html` 都写着"已归档论文按 `ARCHIVE_POLICY` 留档不删"，
而当时这份政策（99 行）**没有一处讲到论文归档** —— 无 `_archive-military`、
无"已归档"状态、无界面显示约定。**两处在引用一份不涵盖这件事的政策。**

下面写的是 **2026-09-19 那次的实例做法**，不是新定的规矩。

### 5.1 什么情况下归档一篇论文（**判据**）

**实际用的判据是一条：这篇论文的产物不能出现在公开演示场合。**

- 案例：`jsjkx2025-kg-rag-qa`（《一种基于知识图谱的检索增强生成情报问答技术》，
  计算机科学 2025）。**方向敏感** —— 军事情报问答。本项目的图谱会在
  **公开演示**与 `web/` 静态站的 3D / 2D 页面上完整展示实体名、
  边与原文证据 ⇒ 这个方向不适合出现在该场合。**2026-09-19 归档**，
  归档时那张图是 **161 节点 / 133 边**（另有 `.bak` 首抽残图 95 节点 / 90 边）。

**⚠️ 归档不是以下任何一件事**（这三条划清界限，否则归档会被当成垃圾桶）：

| 不是 | 那是什么 | 证据 |
|---|---|---|
| **不是"质量差"** | 质量差 ⇒ **留在库里 + 在清单 `note` 里记缺陷** | `rag-qa` 同时有 40% chunk 超时（残图）与 13% 假边，那两条写在 `note` 里，**不是归档理由** |
| **不是"没用了"** | 归档的前提恰恰是它**还有凭据价值** | 见 5.2 第 ② 步：归档 README 专门写了"为什么留而不删"（旧结论的凭据 + 清洗规则升级前的对照） |
| **不是删除** | 见 5.2（动作）与 5.3（界面） | 清单条目、PDF、图谱 JSON、`.bak` 一样不少 |

判不准的时候问一句：**这些实体名、边与证据片段，能不能出现在对外公开的屏幕上？**

### 5.2 归档动作清单（照 `_archive-military/` 那次）

| 步 | 动作 | 实际样子 |
|---|---|---|
| ① | **PDF / 图谱 JSON / `.bak` 移进归档目录** | `data/corpus/_archive-military/`：PDF 2 350 175 B、图 686 245 B、`.bak` 369 675 B |
| ② | ★ **写一份 README** | `_archive-military/README.md`：原路径 → 归档后路径与大小、论文完整信息（作者 / 期刊 / DOI）、**为什么归档**、**为什么留而不删**、**怎么恢复**（三条 `Move-Item`） |
| ③ | **清单条目保留（不删）+ 追加五个字段** | `archived` · `archived_date` · `archived_reason` · `archived_to` · `archived_note` |
| ④ | **重算注册表** | `python tools/build_paper_registry.py`（`archived` / `archived_to` / `archived_reason` 是**从清单透传**的） |
| ⑤ | **跑守门** | `python tools/check_paper_registry.py` ⇒ 八组全绿 |

**③ 的两条口径**（它们正是"为什么它不是删"）：

- **`status` 保持 `downloaded`** —— 它**确实下载过**，文件也仍在归档目录里；
  ⇒ PRISMA（`build_prisma_data.py`）与论文管理页都**不许**把它写成"未下载"；
- **`archived` 是"追加的第五种状态"**，**不改写**既有的四种
  （清单条目 / 已下载 / 已入库 / 上传图）。

**恢复**：归档目录的 README 末尾记着三条 `Move-Item`，把 PDF、图与 `.bak`
移回原位（清单里的五个 `archived_*` 字段同时撤掉、并重跑 build 与守门）。
**但恢复之前请先回答**：凭什么把一份军事情报方向的语料放回公开演示的图里？

### 5.3 归档之后在界面与注册表里怎么体现（**不删 · 不折叠**）

| 位置 | 表现 |
|---|---|
| `data/corpus/_manifest.json` | 条目**在**，五个 `archived_*` 字段与原字段都**在** |
| `web/kg-data/paper-registry.json` | 照常在 `papers[]` 里占一行（三个字段透传） |
| `web/papers.html` 的清单表 | **照常显示**、标「**已归档**」（`.pill.arch` **虚线框**，与「未出图」的实线灰区分开）；**不折叠、不隐藏**；排序时**排最后**（留档不该抢注意力，**但必须在表里**） |
| `papers.html` 的统计口径 | 「已出图 N 篇 / 共 K 节点」**不计入已归档**（`p.in_graph && !p.archived`）—— 归档的图**不是当下可用的资产** |
| `web/prisma.html` + `build_prisma_data.py` | 归入"排除 13 篇"里的「**已归档**」，且**不许**写成"未下载" |

**与第二节的关系**：论文归档 = **方式 B（移入归档目录）的一个特例**，
**不是方式 C（真删）**。它满足选 B 的那个条件 ——
"原位置确实会误导人"：一份方向敏感的图谱留在 `data/corpus/graphs/` 里，
**演示时会被真的展示出来**。默认做法仍是方式 A（原地标注）。

### 5.4 可执行的守门（`tools/check_paper_registry.py`）

政策文字要有代码兜着，否则它只是愿望。**这一节的可执行形式是第 ⑦、⑧ 组**：

| 组 | 判据 | 防的是什么 |
|---|---|---|
| **⑦ 归档标签贴对了人**（2026-09-19 加） | 标了 `archived` ⇒ PDF **不该**在 `data/corpus/` 根下、图**不该**留在 `graphs/` 下，且 `archived_date` / `archived_reason` / `archived_to` **非空**、`archived_to` 是**真实存在的目录**且里面**确实有**这份 PDF；**没标的** ⇒ PDF **应当**在根目录。另加"注册表三列 == 清单"的**透传一致性** | ① **标签贴错对象**（5.5 那次）；② **`archived_to` 指向不存在的目录**（归档标记最常见的假账）；③ **改了清单却没重跑 build** |
| **⑧ 身份一一对应**（2026-09-19 加） | `data/corpus/*.pdf` 的**文件名集合** == 清单里**未归档**条目的 **id 集合**（两个方向都比）；已归档条目的 PDF **不得**出现在根目录 | **野文件**（磁盘上有、清单里没有）、**幽灵条目**（清单里有、PDF 不在）、**归档残留**。⚠️ ⑦ **只遍历清单里已有的条目** ⇒ "磁盘上有、清单里没有"这一类它**永远看不见**；⑧ 不问条目，直接比两个集合 |

**另有一条藏在第 ⑥ 组里**：归档条目**不是特例** ——
它也必须与其它条目一样有合法的 `lang`（取值只有 `zh` / `en`）。

### 5.5 ★ 已知事故与教训：**归档标记曾经贴错对象**

那五个字段的组合是对的，但 2026-09-19 它们**贴在了
`jsjkx2025-kg-completion-llm`**（《大语言模型驱动的多元关系知识图谱补全方法》，
主题中性，PDF 与 179 节点的图都还在 `data/corpus/` 下）**上**；
而真正被归档的 `jsjkx2025-kg-rag-qa`（PDF 与图早已在 `_archive-military/`）
**一条标记都没有** ⇒ 一个**幽灵条目**：该标的那条干净，没归档的那条却顶着"已归档"。

**为什么当时前六组断言全绿**：它们核对的是**数字与取值**（清单数 / PDF 数 /
出图数 / 上传图数 / `lang`），而**这些数字是自洽的 —— PDF 总数没变、
图总数没变，错的只是"标签贴给了谁"。** ⇒ 这就是教训的分量：
**一组自洽的数字，可以完整地掩盖一个错位的身份。**

**已落地的三条**：

1. **标签必须与文件落位对起来**（第 ⑦ 组），不能只对数字；
2. **"数相等"升级为"集合相等"**（第 ⑧ 组）—— 一个野文件 + 一个幽灵条目
   能让两个计数**同时正确**；
3. **修正要留痕**：清单里那两条 `note` 都写着"此前归档标记贴错了对象"，
   **没有把错的那次抹掉** —— 这一节本身就是按那条纪律留下的档案。

**负向测试**（第 ⑦ 组的可信度来自这里）：把标记改回错误状态、**只重建注册表**
⇒ 第 ⑦ 组报红、exit 1，**前六组仍绿** —— 这一条**精确地**抓出本次那种错。

> **只有在文件本身有害时才真删，且必须在提交信息里说明为什么不能用 A。**
