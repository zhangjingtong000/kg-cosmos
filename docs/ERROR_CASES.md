# 错误案例集：KG Cosmos 项目的方法论教训

> 用途：**这是论文素材，不是检讨。**负结果和方法论错误在学术写作中是被低估的资源——
> 它们界定了一个方法的适用边界，而这恰恰是本项目最有价值的部分。
>
> 写作原则：每个错误给出「现象 → 表面解释 → 真实原因 → 判据 → 可迁移的教训」。
> 表象层解释全部被标注为错误，因为**误诊本身就是案例的一部分**。
>
> 时间：2026-09-11 复盘产出。相关文档：`docs/PHASE_REVIEW_2026-09-11.md`（工作台账）、
> `docs/GOLD_METRIC_DIAGNOSIS.md`（指标证伪数据）、`docs/早先的阶段计划.md`（新路线）。

## 摘要：一句话教训

> **在没定义清楚的目标上做优化，测不出改善，于是反复调整——这就是"错上加错"的机制。**
>
> 判据很简单：**修确定的代码 bug（有唯一正确答案）→ 做；优化没定义清楚的目标 → 先定义，再做。**

本项目 100 次提交里，**所有生效的工作都在修确定的 bug，所有失效的工作都在优化一个未定义的目标。**
这条判据事后能 100% 区分两类工作，事前也可以用来决策。

## 案例 1：金标任务定义模糊导致关系标注接近随机

### 现象

设计了"多标注者金标"流程：4 个独立标注者（3 个 DeepSeek agent 用不同阅读策略 + 1 个 GLM）
各自独立标注实体和关系，逐字核对引文，多数投票，规则仲裁。

产出 2 篇金标（93 / 109 个实体，各 65 条关系），报告"平均成对一致率 67.3% / 73.1%"。

后来补算 Krippendorff's α：

| 层 | 论文1 | 论文2 |
| --- | --- | --- |
| 实体 | α = **0.2312** | α = **0.2880** |
| 关系 | α = **-0.0119** | α = **-0.1465** |

**关系层的 α ≈ 0，即接近绝对随机。**

### 表面解释（错）

- 起初：以为标注者能力不足 → 想加更多标注者、改指南
- 接着：以为一致率计算方式不对 → 用了成对 Jaccard
- 再接着：以为需要更细的仲裁规则 → 写了 `GOLD_ARBITRATION_RULES.md`

### 真实原因

**任务本身没有操作性定义。**"这篇论文里 A 和 B 之间是否存在关系"这句话，
对 4 个标注者可以意味着 4 件不同的事：
- 是否显式陈述？（还是可推断）
- 是否只算本文提出的？（还是包括引用他人工作）
- 是否要求句级依据？（还是常识也算）
- 泛化关系算不算？（`X is related to Y` 几乎对任何共现实体成立）

任务定义不闭合时，**多个标注者的分歧不是噪声，而是任务歧义性的直接测量**。
α ≈ 0 正是"这个任务没被定义"的量化证据。

### 关键判据

**α ≈ 0 的含义不是"标注质量差"，而是"该任务在此定义下不可标注"。**
区分方法：看同一批标注者在**不同层**的表现。本项目中实体层 α = 0.23–0.29（可用），
关系层 α ≈ 0（不可用）。**同一批人、同一份指南、同一篇论文，只换了任务层——
这说明问题在任务，不在人。**

### 可迁移教训

1. **一致性 ≠ 效度**。69.9% 的同模型一致率不能作为"金标准确"的证据——它只说明该模型稳定。
2. **4 方、标注量不等时，唯一规范的一致性统计量是 Krippendorff's α**。
   Fleiss' κ 要求每个单元标注者数相同，Cohen's κ 只支持 2 人，都不适用。
3. **⚠️ 本项目的"成对 Jaccard 67.3%"不是 chance-corrected 量，不能叫"一致率"**，
   应改名"成对集合相似度"，且必须与 α 一起报告。
4. **标注者家族必须多样**。PoLL（arXiv 2404.18796）证明跨模型家族评审团优于单一 judge，
   **但要求家族互不相交**。本项目 3 个标注者是同家族（DeepSeek），不满足前提——
   同家族多策略只提供"稳定"证据，**不提供"正确"证据**，必须声明为混杂变量。
5. **自偏好偏差**（Panickssery et al., arXiv 2404.13076）：抽取模型与标注模型同源会污染结果。

## 案例 2：规模口径错配让精确率失去解释力

### 现象

报告的核心指标是实体 P = 0.256 / R = 0.946（云端）。这个组合有两个反直觉特征：
1. P 与 R 极度失衡（0.26 vs 0.95）——正常抽取器不长这样
2. 本地 9B 模型（F1 0.624）反超云端大模型（F1 0.403）

### 表面解释（错，且是双重错误）

- 第一层：以为抽取器过度抽取 → 想加更强的 prompt 约束
- 第二层（我接手后的判断）：以为是匹配口径太严 → 做了口径消融实验

### 真实原因

**金标和系统在回答两个不同的问题。**

| | 问题 | 规模 |
| --- | --- | --- |
| 金标 | 哪些是论文阐述的**重要知识实体** | 83 个四方共识（+10 个仲裁） |
| 系统 | 有哪些**可命名实体** | 344 个 |

**两者测量的不是同一个集合**，相除得到的 P 没有解释力。实测三项数据：

1. **规模指纹**：`|S|/|G| = 3.70`（论文1）、`3.66`（论文2）——同一比值在两篇独立论文上复现
2. **口径消融无效**：strict-exact → similarity 只让 P 变化 **+0.035**（cloud）/ +0.064（local）⇒ 口径不是主因
3. **决定性证据**：256 个"假阳性"中 **88.3% 的实体名字字面出现在它自带的原文证据里**。
   如果这些是错误抽取，名字不可能在原文中找到

**独立佐证（权威论文实测，非本项目测量）**：

> **arXiv 2305.14450**（CoNLL04 错误构成）：Missing spans **53.07%**、
> **Unannotated spans 33.94%**、**Incorrect types 仅 3.43%**。原文：
> *"Unannotated spans accounts for more than 1/3 of all errors ... which raises concerns about the quality of annotated data"*
>
> **arXiv 2504.04083**：*"Frequently, **false positives appear to be correct relations missed by
> the annotators** ... has been shown to **artificially severely deflate performance** ...
> it may be prudent to **re-annotate**"*

### 关键判据

**当 P 和 R 极度失衡、且 |S|/|G| 远大于 1 时，先怀疑口径，别优化抽取。**
诊断方法：对 FP 反查原文——**如果 FP 的名字字面出现在原文里，它是"未收录"而非"抽错"**。

### 附带发现：评测集泄漏

金标 93 = 83 个共识 + 10 个"仲裁翻转"实体。这 10 个全部是**单票（votes=1）候选**，
仲裁时被从"拒绝"翻转为"接受"。检验污染：

```
仲裁接受 10 个 → 系统命中 10/10 = 100%
仲裁拒绝 12 个 → 系统命中 10/12 =  83%
```

**命中率与仲裁决定完全无关** ⇒ 污染假说被证伪，但暴露了更根本的问题：
**在 |S|=344 的密度下，系统"命中一切"，P 退化成"金标抽样率"的度量。**
且仲裁本身脆弱——被接受的 `Abstract Table Representation` 的引文是 `"[25] TEXUS Automatic Documents"`（对不上）；
被拒绝的 `Semantic Data`、`Domain Expert` 其实是合理的。

### 可迁移教训

1. **报告 P/R/F1 必须同时报告 |S|/|G| 绝对值与比值**，否则读者无法判断数值是否可比。
2. **评测集不能包含单票翻转的候选**，否则等于用测试集参与构建验证集。
3. **仲裁环节要有统计支撑**：1 票候选无论接受还是拒绝都无法区分。
4. **"本地小模型反超大模型"这类反直觉结论，先当作口径假象审查**，再考虑是否是发现。

## 案例 3：在错误的度量上优化（最贵的错误）

### 现象

关系 F1 = 0.038 被解读为"关系抽取是短板"，随后启动了一系列优化：

| 尝试 | 结果 |
| --- | --- |
| 调整谓词口径（exact / normalized / family 三档） | F1 **完全相同**（0.043 / 0.043 / 0.043）|
| 换更小的本地模型、调 `num_predict` | 20.9 s/chunk → 16.6 s，仍不可行 |
| 合并抽取调用（一次抽实体+关系） | **更慢**（25.6 s） |
| 改分块大小（500 → 1500 字符） | **更慢**（38.1 s） |
| 反复调云端 API 验证效果 | **¥30+ 余额耗尽** |

### 真实原因

**度量本身无效（分母 α ≈ 0），所以任何优化都测不出改善。**
而"测不出改善"被误读为"改得不够好"，于是继续投入——这是最典型的沉没成本陷阱。

关键反证：**如果谓词选择是瓶颈，口径消融应该带来变化。三档 F1 完全相同，
说明谓词根本不是瓶颈。**这个实验的结果本应立刻终止 prompt 调优方向，但当时没有这样解读。

### 关键判据

**优化之前先问：这个度量有唯一判定标准吗？**
- 有 → 优化有意义，改善可测量
- 没有（如 α ≈ 0、口径未闭合）→ **先修度量，再谈优化**

### 可迁移教训

1. **负结果要立刻用于终止方向**，不能当作"还需努力"的信号。
2. **成本控制的正确姿势不是少调用 API，而是不要在无效方向上调用**。
   本项目最贵的支出不是因为单价高，而是因为**在错误的度量上反复验证**。
3. 速度优化的失败有硬约束原因（8GB 显存 vs 模型规模），
   这类"参数调不动"的情况应尽早通过**量级估算**识别：
   20.9 s/chunk × 5883 chunks = 34 小时，一眼就知道不可行。

## 案例 4：技术选型用"能拿到"代替了"最好"

### 现象

本机环境受限（`huggingface.co` 直连失败，`hf-mirror.com` 的下载路径重定向回被墙的
huggingface.co ⇒ 镜像失效）。在此约束下，我从 ModelScope 成功下载了
`cross-encoder/nli-deberta-v3-base`（704MB）并跑通，随即把它作为方案定下来。

而调研原本的首选是 `Babelscape/mdeberta-v3-base-triplet-critic-xnli`
（RED^FM / ACL 2023 的三元组批判器，阈值 0.75），它在 ModelScope 是 404。

### 真实原因

**把"可行"当成了"最优"。**我确认了首选不可得，就直接采用次选，
没有回头系统评估"还有哪些可下载的更好替代"。

这是"闭门造车"的变体：不是因为不调研，而是**因为调研链条在遇到第一个障碍时就断了**。

### 关键判据

**当首选方案不可得时，需要重新做一轮完整选型——而不是顺序取下一个能用的。**
"能拿到"是约束，"最优"是目标，两者不能互相替代。

### 可迁移教训

1. **技术选型必须记录"为什么选它"**。如果理由是"只有它能下载"，这是一个
   **约束驱动的妥协**，必须在报告里明确标注，并说明是否有更优但不可得的替代。
2. **环境约束要提前摸清**，否则会在错误的地方浪费选型成本。
   本项目在网络可用性上花了大量时间才发现镜像失效。
3. 结论：**"可行"与"最优"是两个独立维度**，方案表应同时列出两项。

## 案例 5：入库层过滤掩盖了抽取层越界

### 现象

Neo4j 库中关系类型**零违规**（严格 15 类），此前被视为一项质量成就。
但全量验证 44172 条**快照**边时发现：

```
越界关系类型的边 237 条（0.54%），共 146 种
含 CONTAINS / REPRESENTED_BY / ADDRESSES / work_at / have / are / friend ...
```

### 真实原因

入库时用 `safe_relation_type` 把越界类型**强制改写为 `RELATED_TO`**，
于是库中"零违规"，而问题被转移并隐藏了——**部分 `RELATED_TO` 的膨胀正是这样产生的**。

### 关键判据

**"下游指标正常"不等于"上游数据正常"。** 需要区分：
- **修复问题**（在源头解决）
- **掩盖问题**（在下游转换）

本项目的做法是后者。掩盖会让问题在别处以更难诊断的形式出现。

### 可迁移教训

1. **过滤/归一化操作必须计数并报告**，否则等于静默丢数据。
   `safe_relation_type` 应该同时输出"改写了多少条、从什么改成什么"。
2. **验证要在多个层做**：库层、快照层、抽取层。只查库层会漏掉被转换掉的问题。
3. 讽刺的是：**越界边的 entailment 均值（0.664）反而高于本体边（0.476）**。
   因为本体边被 `RELATED_TO`/`CREATED_BY` 拖垮了。
   ⇒ **本体划分本身可能不完备**（`CONTAINS`/`REPRESENTED_BY`/`ADDRESSES` 语义上都合理），
   这是一个尚未解决的开放问题，也是"15 类本体"这个设计的隐含风险。

## 案例 6：把"关系抽取质量差"当成结论（一个被推翻的自我判断）

### 现象

我在复盘和此前的判断中写过："关系抽取是稳定短板"、"关系 F1 低是评测协议缺陷"。

### 全量验证推翻了它

对 44172 条边用本地 NLI 做"证据支持度"判定（前提=证据句，假设=关系陈述）：

| 关系类型 | n | **median P(entail)** | both 命中率 |
| --- | --- | --- | --- |
| APPLIES_TO | 3850 | **0.987** | 62.2% |
| USES | 7339 | **0.968** | 61.7% |
| ENABLES | 999 | 0.962 | 68.7% |
| PART_OF | 5816 | **0.946** | 60.6% |
| PRODUCES | 2213 | 0.932 | 61.5% |
| **RELATED_TO** | 9598 | **0.098** | 47.7% |
| **CREATED_BY** | 9060 | **0.001** | **20.5%** |
| **CONTRADICTS** | 243 | 0.008 | 56.4% |

**语义关系类型的中位数都在 0.93–0.99，抽得相当好。**
真正的问题集中在两个"兜底/边缘"类型：`RELATED_TO` + `CREATED_BY`（占 42.7%）。

### 关键判据

**整体均值（0.476）具有欺骗性，必须按类型看分布。**
去掉 `RELATED_TO` + `CREATED_BY` 后，端点齐备的边均值 **0.774**、78.4% ≥ 0.5。

另一个必须看分布的例子：`RELATED_TO` 呈**明确双峰**
（`<0.1` 占 **50.1%**、`>0.9` 占 **38.2%**、中间仅 11.7%）
⇒ **"全删"和"全留"都是错的，正确做法是过滤**。
那一半低分确实无支持，另一半（如 `InteractE ↔ Convolution-based KG Embeddings`，P=0.996）是真的。

### 可迁移教训

1. **聚合指标会隐藏分组结构**。"关系 F1 = 0.04"和"关系抽取质量差"之间没有必然联系——
   可能只是某几个类型坏了。
2. **双峰分布意味着"该过滤"而非"该删除或保留"**。
   判别方法：看分位数而不是均值。
3. **自我判断也要被数据检验**。本案例中，我（AI 助手）先前的判断被自己后来的测量推翻，
   这是正常的——**关键是让测量可复现，而不是坚持结论**。

## 案例 7：过程性错误（工程层面）

| 错误 | 后果 | 教训 |
| --- | --- | --- |
| 黑名单式噪声过滤 | 误杀 `Tables`、`Inclusion Criteria` 等有效实体 | 用标记（`:Noise` + `noise_kind`）代替删除，保留可回滚 |
| 抽取脚本无断点续传 | 一次 HTTP 停顿丢掉 90/111 个 chunk | 逐 chunk 持久化 + `--fresh` 恢复 |
| 读取正在写入的标注文件 | 读到 39938 → 21130 → 51812 字节的三个不同状态 | 合并前必须校验文件完整性 |
| `merge_gold.py` 覆盖已仲裁金标 | 93 → 83，丢失仲裁结果 | 中间产物与最终产物分文件 |
| 节点身份含标签 | `MERGE (x:Label {name})` 使同一实体分裂成多节点（KG 三节点度数 323/323/182 而非 828） | 身份只由业务键决定，标签不是身份 |
| RapidFuzz `WRatio` 默认 0.8 | `UI` vs `build graph.py` = **0.900** 会误合并 | 已知 **Neo4j `FuzzyMatchResolver` 默认就是 `WRatio` + 0.8** ⇒ 照搬必踩坑 |
| 去重改名后未改写关系端点 | 44.1% 的边悬空（44172 → 19466 无端点） | 改名的同时必须改写引用；修复后保留率 55.9% → **94.4%** |

## 案例 8：把"工具用错"当成"事实"——多帧 zstd 静默截断

### 现象

统计 DSH 会话中 `web_search` 调用量以定位成本泄漏。第一次统计返回：

```
web_search 事件总数: 0
api.deepseek.com 出现总次数: 0
```

据此几乎要得出"**没有消耗**"的结论——而事实是主会话单文件就有 **138 次**。

### 表面解释（错）

- 以为是 glob 路径写错 → 改用 `os.walk` 全盘遍历 → **仍然返回 0**
- 以为是文件不存在 → 单独读取该文件 → **count = 138**

### 真实原因

```python
with open(p,'rb') as f:
    zstd.ZstdDecompressor().stream_reader(f).read(200_000_000)
#  → 只返回 187 字节（！）

with open(p,'rb') as f:
    zstd.ZstdDecompressor().stream_reader(f).read()
#  → 全部内容，count = 138 ✅
```

**DSH 的会话文件是多帧（multi-frame）zstd。** `stream_reader.read(n)` 的语义不是
"最多读 n 字节"，而是**在遇到帧边界时提前结束**——它只读完了第一帧就返回。
传入再大的 `n` 也没用。

### 关键判据

**当统计结果与预期严重不符（尤其是"恰好为 0"）时，先验证工具本身，再怀疑数据。**
验证方法：拿一个已知答案的最小样本单独跑一遍，对比两次结果。

本案例中"单文件 138 / 全盘 0"的矛盾本身就是最明确的信号——**如果当时停下来想
"为什么单文件能读到、批量读不到"，会立刻定位到读取方式的差异。**

### 可迁移教训

1. **`read(n)` 在多帧 zstd 上不可靠**，用无参数 `read()` 或循环读到 EOF。
2. **"0 结果"是最危险的统计输出**：它既可能是真结论，也可能是工具故障，
   而两者看起来完全一样。
3. 这次的代价是差点向上汇报"没有成本泄漏",而真实数字是 1044 次调用。

## 案例 9：改动写在了不生效的地方（配置机制误判）

### 现象

定位到 `web_search` 是 DeepSeek 余额消耗源后，在 `~/.dsh/settings.yaml` 写入：

```yaml
tool-web:
  search: false
  fetch: true
```

用户重启 DSH 后，`web_search` **仍然正常工作并仍在调用 DeepSeek**。

### 表面解释（错）

- 以为是"需要重启才生效" → 用户重启了 → 仍无效
- 以为是"配置写错位置" → 反复检查 settings.yaml

### 真实原因

**`tool-web` 的配置根本不从 `settings.yaml` 读取。** 对比源码：

```typescript
// tool-web/src/index.ts —— 配置由 Cordis 组装时传入
export function apply(ctx: Context, config: Config): void { ... }

// llm-deepseek / llm-pi-ai —— 注册了 settings 命名空间才会读 settings.yaml
export const WEB_SEARCH_DEEPSEEK_SETTINGS_NAMESPACE = 'web-search-deepseek'
```

`llm-deepseek`、`llm-pi-ai`、`web-search-deepseek` 能通过 settings.yaml 配置，
是因为它们**主动注册了 settings 命名空间**；`tool-web` 没有，所以那段配置
被完全忽略——**既不报错，也不生效**。

### 关键判据

**配置不生效时，先确认"这个插件有没有注册 settings 命名空间"，
而不是反复调整配置内容。** 判据：在插件源码里搜 `ctx.settings` 或
`*_SETTINGS_NAMESPACE`。没有 → 配置只能通过组装代码或环境变量传入。

### 可迁移教训

1. **静默忽略的配置比报错的配置更危险**——它给人"已经处理好了"的错觉。
2. 改配置前先读该配置的**加载路径**，而不是猜"一般放哪"。
3. 本案例最终有效的路径是：`web-search-deepseek.baseURL`（该插件**确实**注册了
   命名空间）+ 环境变量 + 一处源码适配，而不是 `tool-web.search=false`。

## 案例 10：三层误判的连锁——成本泄漏排查全过程

### 现象

用户报告："聊天用的是 OpenCode 订阅，但 DeepSeek 余额一直在下降。"

### 三次连续误判

| # | 我的判断 | 证伪证据 |
| --- | --- | --- |
| 1 | "子代理跑到了 DeepSeek" | 会话记录里子代理是 `provider: opencode-go`，**一直是对的** |
| 2 | "项目的 `kg_extractor.py` 在调云端" | 那段代码根本没被执行；且已加 `KG_ALLOW_CLOUD` 硬禁用 |
| 3 | "在 settings.yaml 写 `tool-web.search=false` 就能关掉" | 该插件不读 settings.yaml（见案例 9） |

**真凶**：`web_search` 工具。它的后端在 `web-search-deepseek/src/provider.ts` 里
硬编码 `https://api.deepseek.com/anthropic/v1`，**与聊天模型完全无关**。
会话事件 `web/deepseek-search-llm-request` 记录了每次请求的端点与请求体。

### 为什么用户"之前没花过钱"

统计全部 119 个会话文件：`web_search` 从 8 月就一直在调用（08-15 有 65+49+22 次），
**不是新出现的行为**。用户没察觉是因为：

```
8 月:  每天零星几十次
9-11:  一天 300+ 次（密集调研，主对话 138 次 + 15 个子代理）
```

**量级差一个数量级，余额才明显可见。**"之前没花钱"是感知问题，不是事实变化。

### 关键判据

**当"某个东西在花钱"时，先问：这个工具的成本记在哪个账户上？**
成本归属与调用方（谁触发）无关，只与**工具自身的后端配置**有关。
一个聊天走 A 订阅的会话，完全可能因为某个工具的后端是 B 而消耗 B 的余额。

### 最终解决方案（可复用）

`web_search` 用的是 Anthropic Messages 协议 + 服务端工具 `web_search_20250305`。
只要换一个**同样支持该协议的端点**，搜索就能走别的账户：

```yaml
# ~/.dsh/settings.yaml —— 该插件确实注册了命名空间，所以这段生效
web-search-deepseek:
  baseURL: https://opencode.ai/zen/go/v1   # OpenCode Go 原生支持 web_search 服务端工具
  apiKeyEnv: OPENCODE_GO_API_KEY_4
```

实测验证（三步，缺一不可）：
1. `POST https://opencode.ai/zen/go/v1/messages` 返回 200 ✅
2. 带 `tools:[{type:web_search_20250305}]` 时返回 `web_search_tool_result` 块 ✅
3. 端到端：DSH 的 `web_search` 返回真实结果 ✅

**过程中还发现一个必踩的坑**：OpenCode Go 强制要求 `x-opencode-session` 头，
缺失直接 `HTTP 400 cannot be routed efficiently`；而该插件的 config schema
**没有 `headers` 字段**（schmastery 严格校验，多写字段会让整段配置失效）。
解决办法是加一处最小源码适配，用环境变量注入该头，未设置时行为与原来完全一致。

### 可迁移教训

1. **成本排查要按"计费点"而不是"调用方"来找。** 先定位工具的后端端点，
   而不是猜哪个 agent 用错了模型。
2. **会话日志里的事件类型就是审计线索。** `web/deepseek-search-llm-request`
   这种带端点与请求体的事件，是定位外部调用的决定性证据。
3. **换后端时要验证协议兼容性，不是只看 HTTP 200。** 服务端工具
   （`web_search_20250305`）能否被支持，决定方案是否真正可用。
4. **同一个"删除凭据"动作有多个副本**：进程环境变量、DSH 的
   `.credentials.yaml`（优先级更高）、系统机器级变量。删一个不够。
5. 本次排查我连续误判三次，共同点是**没读源码就先下结论**。这与案例 8
   （多帧 zstd）、以及此前的 `hf-mirror` 误判、`krippendorff` 默认测度
   是同一类错误：**工具语义假设错误导致结论反转**。

## 案例 11：统计口径不完整导致严重高估质量

### 现象

复盘文档与质量评估文档中都把"**边保留率 94.4%**"列为一项成果——
从 44172 条边恢复到 41745 条，看起来是一次成功的抢救。

但在完整数据治理后做图库同步时发现：

```
快照应入库边 33677
  端点缺失: 源缺 5688 / 目标缺 5417   ← 10960 条边（32.5%）
去重 + 端点齐全 → 实际可入库 22896
```

进一步按论文统计，**17 篇论文全部出现**，悬空比例 42.9% – 69.4%，平均约 55%。

### 表面解释（错）

- 起初以为是某几篇论文的抽取质量问题 → 按论文统计发现**每篇都一样**
- 接着以为是别名映射没生效 → 查别名表，**10960 条中只有 5 条命中**
- 再以为是统计脚本的 bug → 换口径重算，数字一致

### 真实原因

**"94.4%" 这个指标只覆盖了两类悬空边中的一类。**

| 悬空边的两类 | 成因 | 可修复性 | 是否被 94.4% 覆盖 |
| --- | --- | --- | --- |
| A 曾存在、因改名找不到 | 实体去重改名后未改写关系端点 | ✅ 别名映射可 100% 修复 | ✅ 覆盖 |
| B **端点从未被抽成节点** | 实体抽取与关系抽取的边界标准不一致 | ❌ 无法修复（补建需编造类型） | ❌ **完全没覆盖** |

`rescue_aliases.py` 修的是 A 类，它把保留率从 55.9% 拉到 94.4%——
**但这个分母里根本没有 B 类**。于是 B 类（约 55% 的边）从未进入视野。

### 关键判据

**当一个"修复率"看起来很好时，先问：这个分母覆盖了几种失败模式？**

本案例的判别方法很简单——把失败模式**按成因分类**，逐个检查指标是否覆盖：

```
悬空边 = f(改名残留, 端点从未存在)
         ↑ 已覆盖      ↑ 未覆盖   ← 指标只度量了前者
```

### 可迁移教训

1. **只报告一个"保留率"是危险的**，尤其是当失败有多种成因时。
   正确做法：**按成因分别报告**（A 类保留率 94.4% / B 类占比 55%）。
2. **B 类问题在别名修复"成功"后反而更难被发现**——因为整体数字变好了，
   没人会再去追问剩下的部分。这是"指标改善掩盖新问题"的典型。
3. 从数据角度，B 类本身是一个**有价值的方法论发现**：
   它量化了"实体抽取与关系抽取使用了两套隐式边界标准"这一系统性问题
   （见 `DATA_SNAPSHOT_2026-09-11.md` §3）。
4. 处理上选择**丢弃而非补建**：补建端点需要编造 `type`
   （`Real-world objects represented in knowledge graphs` 算 Concept 还是 Artifact？），
   违反本项目"不猜、可验证"的原则。

## 总结：13 条可写进论文的方法论结论

1. **判据优先**：只做有唯一正确答案的事；没有判定标准的目标，先定义再做。
2. **一致性 ≠ 效度**：α ≈ 0 的含义是"任务不可标注"，不是"标注质量差"。
   用同一批标注者在不同层的 α 差异来定位问题在任务还是在人。
3. **规模口径决定指标可比性**：P/R/F1 必须附 `|S|/|G|`；FP 反查原文可区分"抽错"与"未收录"。
4. **聚合指标掩盖分组结构**：必须按类型/分组看分布；双峰意味着该过滤。
5. **下游过滤不等于上游修复**：归一化/白名单操作必须计数报告，否则掩盖问题。
6. **成本控制的本质是不在无效方向投入**，而非降低单价。
7. **"可行"与"最优"是两个独立维度**：约束驱动的妥协必须显式标注。
8. **"0 结果"需要先证伪工具**：单样本对照是最快的自检手段（案例 8）。
9. **配置不生效先查加载机制**：有没有注册 settings 命名空间，决定配置写在哪
   （案例 9）；静默忽略比报错更危险。
10. **成本归属由工具后端决定，与调用方无关**：排查花钱问题要定位计费点，
    而会话事件类型是最好的审计线索（案例 10）。
11. **修复率必须按失败成因分档报告**：只报一个"保留率"会掩盖未被度量的
    失败模式（案例 11——"边保留率 94.4%"完全没覆盖 55% 的端点从未存在问题）。
12. **同一条规则只写一遍**：写在两处就一定会在某处错开，而且不报错。
    写不了两遍的地方，就加一个"把两遍结果相减"的自检（案例 12）。
13. **留一个能证伪硬约束的检查**：硬约束（如"离线演示"）写在文档里不等于被执行，
    必须有脚本去**实际模拟那个约束**。项目里"离线演示铁律"写了很久，
    但没人跑过一次断网测试，于是主视图一直依赖 CDN 白屏（案例 13）。

## 案例 13：为规避"离线不可靠"而引入了一个必然联网的依赖

**背景**：`docs/早先的内部记录` §1 第 6 条是**离线演示铁律**
——演示现场要有"预构建缓存图谱 + 本地 Ollama"双保险。
但主视图 `web/kg-nebula.html` 的 three.js 一直是从 **unpkg CDN** 加载的。

**怎么发现的**：本轮补完 S3 后回头核对目标，顺手写了个
`tools/cdp_verify_offline.py` 去**实际模拟**断网（CDP 屏蔽外部域名）。
第一次跑就红：`window.__ready = False`、`KGNebula = undefined`、
**页面完全无法启动**。整个 3D 主视图在断网时是一片空白。

**更讽刺的一处在旁边**：`web/official-*.html` 的注释写着

> 唯一改动：把官方示例的 UMD `<script src="//cdn.jsdelivr.net/npm/3d-force-graph">`
> 换成 esm.sh 的 import（**UMD 全局变量在本地离线场景不可靠**）

**理由与效果完全相反**：为了"本地离线场景可靠"而改成 esm.sh，
而 esm.sh 是一个**必须联网**的 CDN —— 这一步把该页唯一的离线可能性去掉了。

**修了什么**：

1. 把 three.js（`three.module.js` + `OrbitControls.js` + `CSS2DRenderer.js`，
   共 1.25 MB）下载到 `web/lib/three/`，importmap 改为本地路径。
   在线验证与离线验证同时通过。
2. 另外 5 个用同一个 three@0.160.0 的历史页面一并本地化。
3. `official-1/2` 改回**本地 UMD**（`web/lib/3d-force-graph.min.js` 就是 1.80.0），
   离线验证通过并出图。
4. **`official-3` 保留联网并如实标注**：它需要 `SpriteText`，
   而 `3d-force-graph.min.js` 内置了自己的 three、`three-spritetext.min.js`
   走全局 `THREE` —— 两份 three 实例不兼容，UMD 路线实测**全黑**。
   要修得把两者都换成 ESM 并让 importmap 指向同一份 three，
   成本高于这一页（官方示例搬运、仅作对比参照）的价值。**没有假装它能离线。**
5. 导航页给仍需联网的 5 个页面标了 `*` 并说明；回归入口加入离线检查。

**两个可迁移的教训**：

**（1）硬约束必须有脚本去模拟它。** "离线可用"不是写进文档就成立的属性，
它需要有东西真的把网断掉再跑一遍。同理，"零云端支出"也需要一个能跑通的
纯本地链路来证明，而不是靠承诺。**凡是写在硬约束清单里的条目，
都应该有一个对应的可执行检查**——否则它只是一句愿望。

**（2）当一个改动的理由与它的效果相反时，通常是理由没被验证过。**
"改用 esm.sh 是为了离线更可靠"——只要真的断一次网就能证伪，
但没人断过。**决策记录里的"因为…所以…"应当至少被验证一次**，
尤其是"为了避免某类问题"这种否定式理由（它最容易想当然）。

**残留（如实记录）**：`community-atlas.html`、`graph-2d.html`、
`force-explorer.html`、`force-graph.html`、`official-3-text.html`
这 5 个历史原型仍需联网。演示主线（导航页 + 五张主卡片）已全部离线可用。

## 案例 12：同一规则写在两处，就一定会在某处错开

**现象**：2026-09-12 删除 165 条 `CONTRIBUTED_TO` 边时，一次牵出了**三处**
"同一条规则被写了两遍"的缺陷。每一处都让数据或指标悄悄偏离，且**都不报错**。

| # | 规则 | A 处 | B 处 | 后果 |
| --- | --- | --- | --- | --- |
| 1 | 本体有哪些关系类型 | `sync_graph.py` 的入库白名单含 `CONTRIBUTED_TO`（**16 类**） | `l5_ontology_audit.py` 按 **15 类**审计 | 同一批边**入库时合法、审计时越界**。L4 报 99.1%，看起来像"治理有代价"，实际那 165 条是 T3.1 自己 relabel 出来的 |
| 2 | 一条边是否被 L5 接受 | `relation_verifier.py` 写 `pass` 字段（用**未舍入**分数判定） | `l5_report.py` / `l5_subgraph.py` 现场比 `entail_prob >= thr` | `entail_prob` 落盘只留 4 位小数，边界值被抹平（实际 0.66995 存成 0.67）。43867 条里 **3 条**判定相反 |
| 3 | 哪些名字不能合并 | `entity_normalize.py` 的 **L1** 调 `is_sensitive()` | 同文件的 **L2** 没调 | `ComplEx`/`Complex`/`ComplEX` 在 L1 被拦住、在 L2 被合并——而"正确拒绝 Complex/ComplEx"正是 T4 保守策略的收益之一 |

**还有一个同类变体**：`l5_report.py` 的"丢弃"写成 `entail_prob < thr`，而"保留"用 `pass`
——两者**不互补**。那 3 条边界边既不进保留也不进丢弃，
于是"保留 27984 + 丢弃 15883 = 43867"里的 **43864 ≠ 43867**。
**互补集合必须由同一个判定函数取补集得到，不能各写一个条件。**

**为什么三处都长期没被发现**：

- 每种写法**单独看都没错**，错误只在**两个数字对不上**时才显形；
- 而它们分散在不同文件、不同章节，甚至只差 **3 条**（0.007%），人眼扫不出来；
- **都不报错**：没有异常、没有告警，脚本正常退出、报告正常生成。
- 第 1 处最隐蔽——它让 L4 从 99.5% 掉到 99.1%，读起来像"治理引入了一点代价"，
  实际是**治理动作自己造出的越界边**。**这是把 bug 当成了现象。**

**对策（本轮已全部落地）**：

1. **单一来源**：`sync_graph.py` 的一致性校验改为引用 `ONTOLOGY_RELS` 本身，不再另抄一份；
   `is_sensitive()` 抽成函数供 L1/L2 共用；`is_supported()` 在 l5 两个脚本里同义实现，
   "丢弃"一律写成 `not is_supported(e)`。
2. **让分歧显形**：`tools/l5_calibrate.py` 里本来就有一节
   「[核实] pass 字段与 `entail_prob >= thr` 不一致的边」——**这一层自检是本轮能快速定位问题的关键**。
   凡是"同一事实有两处表述"，就该有一处专门打印它们的差。
3. **改数据的脚本必须自校验**：`merge_created_by_scores.py` 现在会在写出前逐条比对
   是否与来源文件一致、`hypothesis` 是否与边的方向同向，不一致就**中止写出**。
4. **口径变更要留痕**：`L5_SIX_LAYER_REPORT.md` §1.1 现在固定列出本报告纠正过的
   四类口径问题，避免同一处被反复踩。

**一句话教训**：**同一条规则只写一遍；写不了两遍的地方，就加一个把两遍结果相减的自检。**
