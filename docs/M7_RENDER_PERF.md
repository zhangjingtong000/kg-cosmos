## 二、做法：测**一条曲线**，用仓库里已有的规模梯度

`web/kg-data/` 里本来就有一组密度抽样（**先例，不是我造的**）：
`_density-60 / -150 / -300 / -600 / -1500.json`。

⇒ 拿它们当规模梯度，测"节点数 → 时间"的曲线。
**曲线让"扩语料后会怎样"可以外推**，而不是等扩完了才知道。

## 三、★★ 实测：**三个口径，只有一个半能用**（这是本项最有价值的发现）

```
档位          加载     首绘     flush      rAF(空闲/交互)
60 节点:      192ms    92ms    154.7ms    4.4 / 4.8 fps
150 节点:     887ms   724ms      0.1ms    6.7 / 6.5 fps   ← flush 异常
300 节点:     222ms   104ms    182.1ms    4.5 / 4.6 fps
600 节点:     236ms   116ms    159.6ms    4.8 / 4.9 fps
1500 节点:    309ms   196ms    201.1ms    4.7 / 4.5 fps
主图(19427):  190ms    92ms    174.7ms    5.0 / 5.0 fps
```

### ❌ 口径 A：`requestAnimationFrame` 帧率 —— **在无头下测不出规模差异**

**60 节点 4.4 fps · 1500 节点 4.7 fps** —— 规模差 **25 倍**，帧率差 **0.3**。

**根因**：**无头 Chrome 没有真实显示，`rAF` 被节流到固定频率。**
那个数反映的是「**浏览器认为该画多快**」，**不是「画一帧要多久」**。

**⇒ 而这一条我在写脚本时就已经警告过**（docstring 里写了"无头 ≠ 真机"）——
**这次的实测证明了那个警告是对的，而且给出了具体形态**：
它不是"略有偏差"，而是**完全失去分辨力**。

**⇒ 结论**：**别用无头 rAF 测帧率。** 那 5 fps 与 `ATLAS_DESIGN.md` 的 8.9 fps
**不是同一件事的两个测量**，**不能互相印证**。

### 🟡 口径 B：`flush_draw_ms`（强制一次 `readPixels` 并计时）—— **有信号，但不稳**

- 大部分档落在 **155–200 ms**；
- **150 节点是 0.1 ms** ⇒ 显然那次 `readPixels` 没真跑（上下文/跨源问题）。

**⇒ 它含 GPU 同步开销，单次测量噪声大。** 能用，但**必须多次取中位数**（本脚本只跑了一次）。

### ✅ 口径 C：`load_ms` / `first_paint_ms` —— **有弱但可用的规模相关性**

```
60 节点 192ms/92ms → 1500 节点 309ms/196ms（约 1.6–2.1 倍）
```

**⇒ 这是唯一一个"随规模单调变化且方差可接受"的口径。**
（**150 节点那行的 887/724 ms 是异常值** —— 首次加载要拉 `three.js`，缓存冷。）

## 四、⚠️ 关于 `ATLAS_DESIGN.md:62` 那个 8.9 fps

**它不能被本脚本证实，也不能被本脚本否定**：

- 它测的是 **3000 节点 · 真机 GPU**；
- 本脚本测的是 **≤1500 节点 · 无头软件渲染**。

**⇒ 两个数不可比。** 而 TODO 说"有帧时间基线"时，指的正是那个数 ——
**它现在仍然只是"文档里的一句话"，没有可复跑的来源。**
**⇒ 本脚本补的是"可复跑"这一半，但补不上"真机"那一半**（那需要有人在真机上跑）。

## 六、怎么用

```powershell
python tools/measure_render_perf.py                 # 全部 5 档 + 主图
python tools/measure_render_perf.py --density 300   # 只测一档
```

**⇒ 扩语料之后重跑一次，就有"大规模基线"了** ——
**这正是把它做成脚本（而不是文档里一句话）的意义。**

⚠️ **输出里永远带着一句**：`无头软渲染，仅供相对比较；不等价于真机帧率`。
**那句话是这一项最重要的产出** —— 它防止后人把 5 fps 当成"这台机器的性能"。
