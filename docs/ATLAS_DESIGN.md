# 分面式社区图谱：可读性诊断与设计

> 记录 2026-09-11 把 2D 主视图从「一张全景力导向图」改为「分面式社区图谱」
> 的完整依据。文中所有数字都可用 `tools/diag_subgraph.py`、`tools/diag_atlas.py`、
> `tools/diag_frag.py` 直接复现。

## 1. 问题

2D 主视图在 150 实体 / 960 关系时塌缩成一个致密球体，渲染器主动抑制了全部
标签，屏幕上**没有一个可读文字**（截图留档 `output/shots/user-view-2304.png`）。

第一反应是调布局参数。实验确实改善了均匀度——`adjustSizes: true` 配极低的
`gravity` 把网格占用率从 0.054 提到 0.419（8.6 倍），最密格节点数从 24 降到 3
（对比实验见 `web/_exp-layout.html`）。但**这没有改变"看不清"的结论**：节点
均匀铺开了，连接关系依然糊成一团。

说明问题不在布局，在**取样**。

## 2. 量化诊断

判据用「边/节点」：它直接对应"屏幕上每个节点平均射出多少条线"。

| 子图选法 | 节点 | 边 | 边/节点 | 跨社区边 | 判定 |
|---|---|---|---|---|---|
| 按度数 Top-60 | 60 | 334 | **5.57** | 73.7% | 毛线球 |
| 按度数 Top-150（旧页面） | 150 | 960 | **6.40** | 67.6% | 毛线球 |
| 按度数 Top-300 | 300 | 1861 | **6.20** | 59.8% | 毛线球 |
| 社区配额 Top-150 | 150 | 753 | 5.02 | 75.7% | 仍然糊 |
| 单社区 #3 | 197 | 367 | **1.86** | 0% | 清晰 |
| 度数 Top-150，仅保留社区内边 | 150 | 311 | **2.07** | 0% | 清晰 |
| 2-hop 邻域（cap 150） | 150 | 242 | **1.61** | 43.8% | 清晰 |

两条硬结论：

**（1）「按度数取 Top-N」是在专门挑最坏情况。** 度数最高的节点天然是跨领域
枢纽，它们彼此高度互联。所以取样规模从 60 变到 300，边/节点稳稳停在 5.5~6.4
——这是系统性后果，不是巧合。**越"重要"的节点，取出来越糊。**

**（2）跨社区边是视觉噪声的主要来源。** 毛线球里 60~84% 的线是跨社区的，画
出来全是横穿画面的长线。而社区内部的边天然稀疏——Louvain 本来就是按"内部
稠密"划分的。

### 可读性阈值

以实测为准，**边/节点 ≤ 2.5** 是分界。150 实体 960 关系意味着每节点平均
12.8 条连线，超出阈值 2.6 倍，物理上不可能辨认；这也解释了为什么标签一个都
没渲染出来——sigma.js 在节点过密时会主动抑制标签。

## 3. 为什么是 2D

3D 的核心悖论：**要看清就得丢掉标签，而丢掉标签后节点无法识别**。3D 里节点
会互相遮挡，标签必须依赖屏幕空间投影，任何"看得清结构"的角度都必然让标签
重叠。而 2D 可以把标签做碰撞检测后精确放置。

另外三条实证依据：

- 所有专业图分析工具的主视图都是 2D：Gephi、Cytoscape、Neo4j Bloom、
  Cosmograph、sigma.js。
- sigma.js 官方基准 demo 是 **2085 节点 / 5409 边**的无标签点云，标签只在
  交互时出现（留档 `output/benchmarks/sigmajs-demo-canvas.png`）——说明即便
  主流库，大图也是"点云 + 交互"，而非"全标签"。
- 性能：3D 在 3000 节点时 8.9 fps、首帧 15 秒；2D 在 800 节点 60 fps、首帧
  3 秒。

**结论：2D 作为主分析视图，3D 降级为概览/展示功能**（`kg-nebula.html`
保留为社区级星云展示）。

## 4. 设计：从"切一块"到"按社区组织"

不再试图在一张图里塞进全图，改为**分层递进**：

| 层 | 内容 | 规模 | 边/节点 |
|---|---|---|---|
| L1 首屏 | 18 个社区的连通骨架缩略图 | 每格 40 实体 | 1.35~2.12 |
| L2 社区 | 点击卡片，全屏看该社区 | 40 实体全标签 | 同上 |
| L3 实体 | 点实体看属性与证据链 | — | —（待做） |

每格只有约 340×270 px，因此卡片是**结构缩略图**：画 K 个枢纽的骨架 + 若干
关键实体名，完整内容留给 L2。这不是妥协，而是让首屏在**任何视口**下都不可能
糊——每格的边/节点比被算法锁死。

社区间关系以 50 条主干弧线表达（覆盖 74.2% 的跨社区关系），悬浮某社区时高亮
其对外关联。

## 5. 两个关键算法

### 5.1 `pick_connected`：连通优先的贪心采样

**踩到的第二个坑**：社区内按**全局度数**取 Top-40，取出来是一盘散沙。

原因：全局度数高的节点，其连接主要**跨社区**；它们在社区内部往往没有直接的
边，而是通过社区里度数更低的节点间接相连。实测数据：

```
孤立节点合计 144 / 720 = 20.0%
最大连通分量覆盖率 < 90% 的社区：15 / 18
   社区 17: 主分量覆盖 22%，13 个分量，8 个孤立点
   社区 13: 主分量覆盖 30%
   社区 15: 主分量覆盖 42%
```

后果是缩略图里主体只占约 55% 面积，其余全是飘在外面的散点（留档
`output/shots/atlas-card1.jpg` 的修复前版本）。

**算法**：从社区内度数最高的节点出发，每步加入"与已选集合连接最多"的节点
（并列时取社区内度数高的）。由于每个新节点都与已选集合有边，**取出的 K 个
节点必然连通**。

### 5.2 `cap_degree`：生成树优先的度数上限抽样

节点选取连通了，但按优先级砍边仍会**砍掉桥边**，抽样后重新碎成 2~10 个分量。

**算法**：先 BFS 生成树锁定 `K-1` 条边（生成树边优先级高于 cap，是连通性的
下界），再按 `(关系类型优先级, 端点最大度数)` 贪心补边，每节点最多 `cap` 条。

关系类型优先级把结构性关系（`PART_OF`/`CREATED_BY`/`CITES`）排在泛化关联
（`RELATED_TO`，已知信息量最低、呈双峰分布）之前。

## 7. 复现

```bash
# 子图选取诊断（为什么按度数取样会糊）
python tools/diag_subgraph.py

# 每格抽样参数（K 与 cap 的取舍）
ATLAS_SRC=force-full.json python tools/diag_atlas.py

# 碎片化诊断（连通采样前后的对比）
python tools/diag_frag.py

# 重建前端数据
python tools/build_atlas_data.py
```

前端：`web/community-atlas.html`，数据 `web/kg-data/atlas.json`。

## 8. 已知局限

1. **未归类实体占 46.8%**（7,168 / 15,315）。这些节点未参与 Louvain 划分，
   目前在首屏底部一行说明中披露，未可视化。这是社区划分本身的覆盖问题，
   值得单独处理。
2. **每社区只呈现 40 个代表**。选择依据是"连通且度数高"，会漏掉社区内孤立
   但语义重要的节点。
3. **首屏不画跨社区边**，只用 50 条主干弧线近似（覆盖 74.2%）。
4. **标签用矩形碰撞检测**，密集处会主动省略部分标签——这是保证"永不重叠"的
   代价，L2 视图会展示全部 40 个标签。
5. 布局是每次加载现算的（ForceAtlas2，浏览器端），未做种子固化；同一社区在
   不同次加载的形状会有细微差异。
