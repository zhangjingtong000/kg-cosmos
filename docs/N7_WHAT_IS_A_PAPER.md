## 一、结论先说：**"一篇论文"在四层里是四个意思**

| 身份 | 由什么决定 | 数量（2026-09-17 实测） |
|---|---|---|
| **① 清单条目** | `_manifest.json` 的一条（arXiv id） | **28** |
| **② 已下载** | `data/corpus/<id>.pdf` 存在 | **28** |
| **③ 已入库** | `data/corpus/graphs/<id>.json` 存在（**且非 0 字节**） | **17** |
| **④ 上传图** | `data/<gid>/graph.json` 存在（**gid ≠ arXiv id**） | **3** |

**⇒ 所以"一篇论文"这句话本身是不完整的** ——
**「我传过哪些」问的是 ④，「语料有几篇」问的是 ③，「我下载了多少」问的是 ②。**

**这正是 TODO 说 K2「被严重低估」的原因**：
它看起来是"加一个列表页"，实际**要先决定列表是按哪一层列的**。

### ⚠️ 还有第五层，最容易漏：**上传任务**

`data/upload-tasks/*.json` 里有 **8 条**，而只有 **3 条**产出了图。
剩下 **6 条**是**失败或中断的上传**：

```
4e570fea  __probe_2.pdf          error / error
565c2dc1  empty.pdf              interrupted / parse     ← **空文件**
5a472e23  empty.pdf              interrupted / parse     ← **空文件**
7dc6079d  __probe_1.pdf          error / error           ← **探针**
beb6e555  2506.09566v1.pdf       error / error
c4266bac  2506.09566v1.pdf       error / error
```

**⇒ 「我传过哪些」如果只看 ④（图），会把用户传失败的 6 次全部漏掉。**
传失败了也是"传过" —— **用户最想知道的恰恰是"我那次为什么没成"。**

## 二、关联键：**它一直存在，只是没人连**

TODO 说"没有关联键"是**对的**（没有**显式的外键字段**），
但**文件名就是那把钥匙**，而它在**两处**都存着：

```
data/upload-tasks/<gid>.json     id = gid      filename = "2506.09566v1.pdf"
data/<gid>/graph.json            source.name = "2506.09566v1.pdf"
                                 source.id   = gid
_manifest.json                   id = "2506.09566v1"
```

**⇒ 关联链**：

```
gid  →  graph.json 的 source.name  →  去掉 .pdf  →  arXiv id  →  _manifest.json
```

**⇒ 已实现**：`tools/build_paper_registry.py`（产出 `web/kg-data/paper-registry.json`）。
它**只做连接，不做猜测**：

- 文件名**必须严格匹配 arXiv id 正则**（`^\d{4}\.\d{4,5}v\d+$`）才建立关联；
- 匹配不上的**如实标为 `None`**（`__probe_2.pdf` / `empty.pdf` 就属于这类）。

### ★ 两套 id 体系**不合并**

| | arXiv id | gid |
|---|---|---|
| 例 | `2506.09566v1` | `3e38f803` |
| 性质 | **语义 id**（人可读、可引用、可去 arXiv 查） | **随机 hex**（机器生成） |
| 谁产生 | 检索/下载流程 | `POST /upload` 当场分配 |

**⇒ 注册表把它们连起来，但不合并。**
合并会丢掉一个事实：**"这份图是用户当场传的"**（而不是从语料库里来的）。

**⇒ 而这个事实有直接后果**：实测发现——

```
3e38f803  2506.09566v1.pdf  → 2506.09566v1   1045 节点 / 1902 边
ad690dfb  2506.09566v1.pdf  → 2506.09566v1    793 节点 /  951 边
```

**同一篇被传了两次，两次的图不一样**（1045/1902 vs 793/951）。
**⇒ 如果不保留 gid，这件事在数据里就看不出来了** ——
"我传过哪些"会显示成一篇，而**用户实际传了两次、得到两份不同的图**。

## 三、已知的洞（**如实列出，不圆场**）

| # | 洞 | 处理 |
|---|---|---|
| **1** | **作者缺失** —— `_manifest.json` 里**没有 `author` 字段** | 注册表里**如实留 `None`**，**不去猜**。要补得从 PDF 首页解析（K2 的"半天元数据解析"就是这件）。**猜出来的作者比没有更糟。** |
| **2** | **`_manifest.json` 的 `status` 全是 `downloaded`** | 它**不能**用来判断"入库没有" —— 那个信息在 `web/kg-data/corpus-index.json` 的 `in_graph` 里。**注册表两个都读**。 |
| **3** | **0 字节的图文件** | `data/corpus/graphs/` 下有若干 **0 字节**的探针残留（`ch-local-*` / `count-*` / `gold-*` / `probe-*` / `tmp2-*` / `work-*`）。**注册表按"非 0 字节"判定入库**，否则 17 会变成 24。 |
| **4** | **上传了但文件名不是 arXiv id 的连不上** | 本库目前只有 `__probe_*.pdf` / `empty.pdf`（都是测试残留）。**保留为 `None`**，不为它们编造 id。 |

## 四、第二条 N7：**gold 源文件重复且页数矛盾**（已核实）

```
data/gold/SOURCE-2401.04507v1-p1-10.txt   64528 B  sha256=c5231c61f707301a...
data/gold/SOURCE-2401.04507v1-p1-15.txt   64528 B  sha256=c5231c61f707301a...   ← **完全相同**
data/gold/SOURCE-2012.00456v1-p1-12.txt   44150 B  sha256=60167b935e8362e8...
```

**⇒ 确认**：`-p1-15.txt` 与 `-p1-10.txt` **逐字节相同**，
即 **10 页的正文被复制成了"15 页"**。

**⇒ 而口径册以「10 页」为准**（两处都这么写）：

```
METRIC_CALIBERS.md:79     **只有 2 篇**（2012.00456v1 12 页 / 2401.04507v1 **10 页**）
OPTIMIZATION_PLAN.md:21   金标共 2 篇（2012.00456v1 12 页 / 2401.04507v1 **10 页**）
```

**⇒ 所以 `-p1-15.txt` 是错的那一份。**

### 处理：**按 `ARCHIVE_POLICY`，不删**

它被**改名归档**，并在旁边留一张说明：

```
data/gold/SOURCE-2401.04507v1-p1-15.txt
  → data/gold/_archive/SOURCE-2401.04507v1-p1-15.txt.DUPLICATE-OF-p1-10
  + data/gold/_archive/README.md（写明 sha256 相同、口径以 10 页为准、以及为什么留）
```

**为什么留而不删**：这条记录本身是**一条证据** ——
它证明"页面范围"这个字段**曾经被写错过**，
而 `REVIEW_ROUNDUP.md:81` 正是靠它才能指出这个缺陷。
**删掉它，那个缺陷就只剩一句无凭据的话。**
