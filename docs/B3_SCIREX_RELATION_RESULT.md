## 二、根因：**两层失配**（都实测过）

### ① SciREX 的槽位实体有 46% 根本不在正文里

SciREX 的金标四元组长这样：

```json
{"Method": "RED30", "Task": "Image_Super-Resolution",
 "Material": "BSD100_-_4x_upscaling", "Metric": "PSNR", "score": "27.40"}
```

它标的是**论文表格里的一行**。实测（前 3 篇）：

```
18168aea…  槽位实体 6 个 · 其中**字面出现在原文** 4 个
           不在原文里的：bsd1004xupscaling · set54xupscaling
2f97ee95…  槽位实体 7 个 · 字面出现在原文 3 个
           不在原文里的：percentageerror · switchboardhub500 · vggresnet…（超长拼接名）
249b3b74…  槽位实体 11 个 · 字面出现在原文 6 个
           不在原文里的：300d2layerbicaslstm · sst2binaryclassification
合计：24 个槽位实体，**13 个能在纯文本里找到（54%）**
```

**⇒ 46% 的槽位实体在表格/图里，抽取器看不到它们。**

### ② 剩下 54% 虽在正文，但抽取器把它们抽成了"**概念**"

从产物里的 `sample_fp`（假阳性样本）能直接看到我们抽的是什么：

```
"Image Restoration" · "gradient vanishing" · "ill-posed inverse problem"
"corruption distributions" · "computer vision tasks" · "super - resolution"
```

**⇒ 全都是叙述文本里的概念性短语**，而 SciREX 的槽位是**方法名 / 数据集名 / 指标名**。

**⇒ 抽取器没有"槽位意识"** —— 它不知道 `RED30` 是"方法"、`PSNR` 是"指标"、
`BSD100` 是"数据集"，于是把"RED30 在 BSD100 上达到 PSNR 27.40"这句话
**抽成了概念之间的关系（或干脆没抽）**，而不是那三条槽位三元组。

### ③ 附加因素：`pred_triples` 只认三种类型

`pred_triples` **刻意只保留** `APPLIES_TO` / `USES` / `MEASURES`
（理由是对的：`CITES`/`PART_OF` 与 SciREX 的槽位不是一回事）。
⇒ 如果抽取器把那条语义表达成了别的类型，**即使端点都对也匹配不上**。

## 三、★ 这个结果推翻了 TODO 的预期

TODO 对 B3 的期望是（`_scirex_eval.py:65-70` 也写着）：

> **② 从"抽取侧"再验证主结论**：若在 SciREX 的**槽位式**关系上表现
> **明显好于我们自己那套开放式谓词**，就与"标注侧"同构印证了
> 「**可标性取决于协议结构化程度**」

**实测是相反的**：`rF1 = 0`。

### 但这**不**推翻主结论 —— 因为它测的不是同一件事

| | P3 协议阶梯（主结论的来源） | B3（本实验） |
|---|---|---|
| 问的 | **标注者**在"完全开放 / 给类型表 / …"下的**一致性 α** | **抽取器**在 SciREX 槽位上能不能抽对 |
| 变的 | **协议的结构化程度** | **实体类别的先验知识（槽位意识）** |
| 结论 | 结构化程度 ↑ ⇒ α ↑ | **没有槽位意识 ⇒ 抽不出来，与协议无关** |

**⇒ 诚实的表述**：

> **B3 说明的是"抽取器缺少表格理解与槽位意识"，不是"协议结构化不管用"。**
> 两者**不能互相印证，也不能互相否定** —— 它们测的是链条上不同的环节。
> **B3 的失败恰恰说明：协议结构化（P3 那一侧）之后，
> 抽取器这一侧还有一个独立的、尚未解决的瓶颈。**

**这比"印证成功"更有信息量** —— 它定位了下一个要攻的点。

## 四、诚实的边界

| # | 边界 | 影响 |
|---|---|---|
| **1** | **6 篇全零已核实（不是只看前 2 条）** | `rtp = 0` 是 **6/6**，合计 40 条金标 / 429 条预测零交集 —— **强信号**，但样本仍只有 6 篇 |
| **2** | **`max_chars=500`** | 每块 500 字符 ⇒ **表格很可能被切碎**，这本身放大了"看不见表格实体"的问题 |
| **3** | **没测"如果把表格单独喂进去会怎样"** | 那是**验证性实验**，未做 ⇒ **"表格理解缺失"是推断，不是直接测量** |
| **4** | **`fold()` 的归一化是否还吃掉了一些匹配** | 未逐条核对；不过端点在正文里就对不上（§二①），**归一化不是主因** |
| **5** | **`score` 字段不参与** | SciREX 的 `score`（如 `27.40`）是独立字段、不是关系槽位，**本实验按设计忽略它** |

**第 3 条是最该补的**：把 SciREX 原文里的表格区（用 PDF 结构或正则识别）
**单独作为一个 chunk 喂给抽取器**，再看 `rtp`。
若那时 `rtp > 0` ⇒ **直接证明"瓶颈在表格"**；若仍为 0 ⇒ 问题在槽位意识。

## 五、结论与建议

**结论**：**B3 的 `rF1 = 0` 是一个"定位到瓶颈"的负面结果**，
而不是"映射写错了"或"抽取太差"。

**建议（写进 TODO，不由本次实施决定）**：
1. **加一个表格通道**：把 PDF 表格区单独抽成文本 chunk（PyMuPDF 的 `find_tables` 或按列对齐识别）；
2. **加槽位提示**：prompt 里明确"方法名/数据集名/指标名也要作为实体抽出，
   类型分别给 `Method`/`Dataset`/`Metric`"；
3. **重跑本实验**，看 `rtp` 是否从 0 变成正数 —— **那才是对 §三 那张表的真正回答**。

**在这三条做完之前，B3 只能算"跑过并定位了瓶颈"，不能算"验证了主结论"。**
